# 0001. 采用 Flutter 作为三端 UI 框架

- 状态：Accepted
- 日期：2026-11-06
- 决策人：TL
- 关联：计划文档 §1、§6；§12 复用策略

## 背景

需要在 Android / Windows / macOS 三端交付同一套提词器体验，包含高频文本滚动（60 fps）、镜像渲染、悬浮窗、外接屏与本地 ASR 集成。团队规模小（3 人），要求最大化复用、缩短交付周期，同时保留 iOS/Linux 扩展位。

## 决策

采用 **Flutter 3.x（Dart 3）+ Riverpod 2 + drift** 作为统一应用框架；平台能力通过 federated plugin（`tp_platform`）下沉，核心算法用纯 Dart 包实现。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Flutter | 单代码库三端；Impeller 稳定帧率；Dart 纯逻辑易单测；sherpa-onnx 有官方绑定；M3 原生支持 | 桌面生态相对年轻；包体较大；原生缺口需自补 | **采用** |
| React Native | JS 生态大 | 桌面支持弱；高频滚动/音频 FFI 成本高；三端一致性差 | 否决 |
| Kotlin Multiplatform | Android 原生体验好 | 桌面 UI 仍需各写；团队学习成本；文本渲染需自建 | 否决 |
| 三端原生 | 平台体验最佳 | 3 套 UI + 3 套逻辑，3 人团队无法在 16 周交付 | 否决 |

## 影响

正面：

- 约 88% Dart 代码共享，UI/业务/算法一套；
- 核心算法可离线单测，评测集可直接跑；
- M3 组件与 `dynamic_color`、`flutter_adaptive_scaffold` 直接复用，降低 UI 与无障碍成本；
- 复用成熟插件（悬浮窗、窗口、热键、多窗口），WBS 净减 44 人日。

负面：

- 桌面端悬浮/多显示器/全局热键仍需原生薄封装（约 12% 代码）；
- 安装包体积高于原生（模型另计）；
- 某些平台特性需等待插件成熟，存在维护风险（R-21）。

## 验证方式

M0 三端 Demo：60 s 连续识别驱动滚动，帧率 ≥ 55 fps、内存 < 400 MB、冷启动 < 1.5 s；若不达标，评估桌面端改用原生壳 + 共享核心（需新 ADR）。
