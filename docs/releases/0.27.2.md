# 0.27.2（2026-11-11）

> 状态：**已出 release（对齐窗口锚点修复）** ｜ 平台：Android（APK） ｜ 版本口径：`version: 0.27.2+2032`
> 主题：修掉快速朗读时的对齐窗口错位（zh_fast 延迟的真正根因），并补上端到端延迟预算

## 这个版本能做什么

- 快速朗读时不再出现「锚点先跳到后面几行、滚行冻结、到段尾才猛追」。快速段（`p0-zh-fast-01`）跟随延迟 P50 从 2220 ms 降到 880 ms，P95 从 6454 ms 降到 1010 ms，命中率 80% → 100%。
- 防跳红线没有放宽：误触发 0、单次跳读 0 行、任意 10 s 累计跳行 0 行，与 0.27.1 完全一致。
- 其余行为与 0.27.1 相同（跳读棘轮、累计跳行预算、重锚冷却、等待态等均未改动）。

## 根因：不是算力，是对齐窗口钉错了起点

这是**缺陷修复**，不是性能调优。

- 识别文本是「本分句累积」的：端点之前，每次 partial 都在尾部追加，阅读位置始终落在文本末尾附近。
- 旧实现让 DP 窗口跟着阅读位置滑动。这样一来：
  1. 文本前缀落在窗口之前，只能记成「插入代价」；
  2. DP 的单调带宽是 `|i-j| <= 40` 音节。一条分句超过 40 音节（约 8 秒快速朗读）后，真实路径直接落到带宽之外；
  3. DP 于是选择一条**看似更便宜、实际错误**的路径：「删掉台本前缀 + 把文本尾巴对到更后面几行」。
- 后果（真机与评测都可复现）：锚点在 8.1 s 起 1→2→3 连锁前跳，置信度掉到 0.19–0.31，滚行被冻结，直到 21.5 s 端点出现新分句才追回——这就是 `zh_fast` P50 2220 ms / P95 6454 ms 的来源。

修复（`packages/core_alignment/lib/src/aligner.dart`）：

- 窗口起点改为**分句起点**：端点后重设；文本公共前缀相对上次骤降（< max(3, 上次长度×0.5)）时也视为新分句；阅读位置远超「分句起点 + 文本长度」可解释范围时作废旧起点（覆盖手动跳行、断点续读）。
- DP 首行台本前缀**免费跳过**（`dp[i] = 0`）：识别文本起点未必正好落在窗口起点，前缀不应被罚成删除。
- 窗口长度自适应长分句：`n = min(reachable, max(windowW, m + 2 * band))`，上限 600。带宽只约束分句内部的局部错位，不再限制分句长度。

## 变更

### Fixed

- 长分句对齐窗口错位导致的锚点连锁前跳、置信度塌陷与滚行冻结（见上文根因）。

### Added

- `AlignMetrics` 对齐性能计数（默认关闭，评测打开）：DP 次数/格数/微秒、预筛额外 DP 次数、重锚扫描与 DP 次数，随评测报告写入 `latencyBudget`。
- 回归用例「单条长分句（超过带宽 40 音节）仍能对齐到已说位置」：n = 5…120，断言锚点停在当前行、跟上已说位置、置信 > 0.6。

### Changed

- 阅读页正文子树缓存：partial 仍逐条 `setState`，但正文只依赖「排版快照 + 当前视觉行 + 主题/对齐/标记数/滚动带位置」；键不变时返回同一 Widget 实例，Flutter 跳过整棵子树 update。

## 端到端延迟预算（为什么没有去动解码、线程和模型）

| 段 | 环境 | P50 | P95 |
|---|---|---|---|
| 采集分片 | 真机 | 80 ms | 80 ms |
| 音频线程排队（`asr_lag.backlogMs`） | 真机 | 0 ms | 0 ms |
| 解码（每次 `decode`） | 宿主 | 0.0 ms | 3.2 ms |
| 对齐 DP（每次 partial） | 宿主 | 58 µs | 384 µs |
| 产生新行 → 重绘 | 真机 | 一帧内 | 7.07 ms |
| **ASR 出字间隔（最大项）** | 宿主/真机同 | **320 ms** | **1280 ms** |

- 最大项是模型 chunk（320 ms）决定的出字节奏，不是算力；解码 + DP + 重绘合计不足端到端的 2%。
- 真机 `decodeMs` 1–20 ms/分片、RTF 8.6–9.3%；宿主 RTF 1.14%，`decode` 762 次对 12329 个分片（`isReady` 门控，无重复喂入）。
- 真机界面帧：build 0.42 / 0.81 ms、raster 2.71 / 4.48 ms、`totalSpan` p95 7.07 ms（3667 帧，janky 8 帧；数据来自 0.27.0 装机存档，本版未改正文渲染路径）。

按收益逐项评估后的结论：

| 项 | 结论 |
|---|---|
| 对齐窗口起点 | **修**（本版核心，收益最大） |
| 解码线程数 2 | 不改：RTF 1.18% → 0.99%，跟随延迟完全不变，单线程省电 |
| `decode_chunk_len` | 不动：模型 chunk 固定 320 ms，喂 20/80 ms 都不改变出字节奏 |
| 重复喂入 | 不存在：762 次 decode 对 12329 个分片 |
| partial 不变时跳过重解码 | 已天然成立：识别器只在文本变化时产出 |
| 增量对齐（只重算变化段） | 不做：单次 DP 58 µs，收益可忽略，正确性风险大 |
| 窗口/带宽收紧 | 不做：收紧会重新制造本版修掉的假路径 |
| `span<3` 早退 | 已生效（记 0 置信、不推进），DP 仍跑但只有 µs 级成本 |
| bilingual 209 MB → 14M | 不换：解码只占 RTF 1.2%，延迟无收益，且会丢中英混说 |
